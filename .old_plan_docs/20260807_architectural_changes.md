# CoChem-BASE Architectural Changes (2026-08-07)

This document outlines the requisite architectural refactoring for the `CoChem-BASE` module to seamlessly integrate with the `Method Matrix` and the newly designed `SCRIBE`, `TOPOS`, and `TORQ` inter-dependencies. Implementing these architectural changes is the strict prerequisite before generating the comprehensive execution workflow.

## 1. Core Engine Transformation: Job Manager & Time-Tiers
**Target File:** `core_engine/cochem_core_job_manager.py`

**Current State:** 
The `JobManager` class is a simplified placeholder that logs string states (`submitted`, `running`) without any actual subprocess tethering or asynchronous time-tracking.

**Required Architectural Change:**
- **The 10-Tier Execution Tether:** The `JobManager` must be completely rewritten to inherit the 10 temporal wall-clock tiers (from 10 seconds to 1 month) defined in the *Method Matrix*.
- **Asynchronous Execution & Killing:** The manager must utilize `asyncio.subprocess` to spawn the `ORCA` or `MACE` binaries. It must actively track the wall-clock time and forcefully send `SIGTERM` (followed by `SIGKILL` if unresponsive) if the calculation breaches its tier budget.
- **Hardware-Calibrated Tiers:** Instead of static timeouts, `CoChem-BASE` must run a 5-minute calibration benchmark upon installation (via `cochem_core_hardware_profiler.py`) to align the 10 time-tiers with the specific hardware's TFLOPS capability.

## 2. Hardware-Aware Routing & MLFF Fallbacks
**Target File:** `setup/cochem_setup_orchestrator.py` and Config Compilers

**Current State:** 
The orchestrator successfully resolves operating system layers (WSL vs Codespaces) but blindly passes calculations to the quantum engines without inspecting the chemical inputs against the hardware.

**Required Architectural Change:**
- **CUDA vs CPU Detection:** `cochem_setup_orchestrator.py` must probe the active environment for CUDA accelerators using `nvidia-smi` or `torch.cuda.is_available()`. If a Codespaces CPU environment is detected, MACE calculations must be dynamically rerouted to `g-xTB` with a UI educational popup explaining the graceful degradation.
- **QCxMS Binary Detection:** The orchestrator must silently detect if the `QCxMS` binaries are compiled in the environment. If missing, it dynamically disables the Mass Spectrometry UI tier.
- **Element Boundary Fallback:** The input generator must parse the `.xyz` or SMILES string *before* passing it to TOPOS. If it detects elements outside the parameterized boundaries of `MACE-OFF24m` (e.g., transition metals), it must preemptively rewrite the config block to trigger the `AIMNet2` fallback to prevent runtime crashes.

## 3. Global State Management: Transitioning to HDF5
**Target File:** `core_engine/cochem_core_registry_manager.py`

**Current State:** 
`CoChem-BASE` relies heavily on writing and parsing flat `.json` registries (`cochem_mint_registry.json`, `cochem_deployment_manifest.json`) to communicate between modules.

**Required Architectural Change:**
- **Unified HDF5 Registry:** To support the massive conformer matrices generated by the TOPOS GOAT loop and the 3D DVR grids generated by TORQ, the flat JSON architecture must be deprecated.
- **Memory-Mapped Arrays:** `cochem_core_registry_manager.py` must initialize a master `cochem_state.h5` tensor. This file acts as a shared memory-mapped (`mmap`) database. BASE will write the initial configurations here, TOPOS will append its conformer geometries and Hessians, and TORQ will append the anharmonic scans. SCRIBE will later pull directly from this HDF5 file in memory-aware chunks to prevent I/O crashing.

## 4. Advanced Computational Keyword Injection
**Target File:** `core_engine/cochem_core_config_compiler.py`

**Current State:** 
The config compiler generates functional `ORCA` inputs but lacks the nuanced logic required to prevent linear dependencies or manage advanced Counterpoise combinations.

**Required Architectural Change:**
- **Dynamic BSSE Suppression:** If the user specifies scaling to the Complete Basis Set (CBS) limit or requests TightPNO DLPNO-CCSD(T), the compiler must auto-suppress the `%geom Counterpoise` block to prevent mathematical overcorrection.
- **Composite Method Safety:** Hardcode logic to block external Counterpoise flags if methods like `r2SCAN-3c` or `wB97X-3c` (which inherently contain geometrical counterpoise) are invoked.
- **AutoAux Injection:** Build a subroutine that detects the presence of diffuse basis sets (`aug-cc-pVTZ`) and injects the `AutoAux` keyword while upgrading the grid to `DefGrid4` (mandatory for `RIJCOSX` with double hybrids).
- **ExtremeSCF Guardrails:** Guarantee that `ExtremeSCF` is appended to all single-point scripts generated by BASE to ensure absolute wave-function convergence prior to extrapolation.

## 5. Strict Inter-Module Sync Validation
**Target File:** `core_engine/cochem_core_subprocess_broker.py` (New feature)

**Current State:** 
Modules execute independently. If the user pulls an update to `SCRIBE` but leaves `TOPOS` on an older schema, the pipeline will crash mid-execution.

**Required Architectural Change:**
- **Schema Validation Pre-flight:** Before `BASE` allows any computational job to execute, it must ping `TOPOS`, `TORQ`, `SpycFit`, and `SCRIBE` to fetch their internal schema version strings. 
- **Execution Lock:** If the versions do not perfectly match the `cochem_deployment_manifest.json` schema list, the `SubprocessBroker` must halt the pipeline and force the user to update the entire CoChem repository suite, maintaining absolute architectural integrity.

## 6. Interactive Setup & Validation Regimen (Start_Here.ipynb)
**Target File:** `Start_Here.ipynb` and `test_suite/`

**Current State:**
The Jupyter notebook provides a basic static button for Silo generation and Dashboard launching, but lacks robustness in detecting prior setups, handling new module installations, or verifying the calculation environments before job handoff.

**Required Architectural Change:**
- **Stateful Installation Tracking:** The `Start_Here.ipynb` UI must proactively detect if the setup stage has already been completed. It should prompt the user to "Keep previous setup" (which triggers path and directory validations for `cochem_base_silo` and `CoChem_Artifacts`) or to execute a "New Install" (which dynamically creates or clears the `Silos` directory based on user input).
- **Module & Environment Validation:** If the user keeps the previous setup, the system must assert the presence of `BASE`, `TOPOS`, `TORQ`, and `SCRIBE` modules within the `modules/` directory. Furthermore, it must automatically execute rapid (<1s) ORCA single-core and multi-core test jobs to definitively prove the Calculation Environment is functional.
- **Dynamic Calculation Path Mapping:** The notebook's Interface must allow the user to select their Interface Environment (e.g., WSL, OrbStack, Codespaces) and Calculation Environment (e.g., WSL, HPC, GitHub Actions). For local Unix environments, it must automatically attempt to detect `orca` and `openmpi` paths.
- **Automated ORCA Tarball Extraction:** The UI must feature an explicit button for uploading or selecting an ORCA Linux `.tz` or `.tar.xz` file. The backend logic must autonomously extract this archive, configure the internal paths, and register the ORCA binaries globally for the CoChem pipeline.
- **Dedicated Testing Suite:** A new package (`CoChem-BASE/test_suite/`) must be constructed to orchestrate these checks. It must contain discrete Python modules (`test_environment.py`, `test_modules.py`, `test_orca.py`, `test_mpi.py`) that return programmatic success/failure flags to the UI, offering didactic feedback on how to resolve failing tests.
