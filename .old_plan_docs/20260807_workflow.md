# CoChem-BASE Master Execution Workflow (2026-08-07)

This document maps the complete, step-by-step execution workflow for the `CoChem-BASE` orchestration module. This workflow fully implements the principles outlined in the *Method Matrix*, *Improving LAM Microwave Predictions*, and the *20260807 Architectural Changes* documents, establishing an unyielding foundation before any chemistry is executed.
## Stage 0: Pre-Flight & Installation Validation (Start_Here.ipynb)
1. **Silo & Registry Validation (Cell 1):**
   - The script detects if `CoChem_Artifacts` exists. It asks the user to choose "Keep previous setup" or "New Install".
   - **Keep:** Validates the environment is currently `cochem_base_silo` and `CoChem_Artifacts` is intact. Prints readiness indicator.
   - **New:** Prompts the user for a custom `CoChem_Artifacts` location. It forcefully deletes any prior `CoChem_Artifacts/Silos` in that path, creates a fresh `Silos` directory, and establishes the minimal environment.
2. **Environment & Core Executable Testing (Cell 2):**
   - The system checks if module validation has previously passed. Prompts for "Keep" vs "New".
   - **Keep:** Scans `D:\_CoChem\CoChem_Artifacts\modules` for BASE, TOPOS, TORQ, and SCRIBE. Executes two rapid (<1s) ORCA test jobs (one single-core, one multi-core using OpenMPI) via the `test_suite`. If tests pass, indicates full readiness.
   - **New:** Spawns a GUI to select the Interface Environment (WSL, OrbStack, Deb, Codespaces) and Calculation Environment (WSL, OrbStack, Deb, GitHub Actions, HPC).
3. **Automated Path Configuration:**
   - If a local Calculation Environment is chosen, the UI attempts to silently detect the paths for `orca` and `openmpi`.
   - If an external environment is chosen (GitHub Actions / HPC), explicit predefined paths are loaded.
4. **Tarball Ingestion:**
   - The UI provides an explicit upload button for an ORCA Linux `.tz` / `.tar.xz` file. When triggered, the file is automatically extracted, and paths are updated dynamically.
5. **Execution of the Test Suite:**
   - A `< 1 second` single-core job and multi-core job are submitted through `test_suite/test_orca.py` and `test_mpi.py`. The UI flags success/failure. If failures occur, diagnostic recommendations are provided to the user.

## Stage 1: UI Initialization & Hardware Profiling
1. **Launch:** The user initiates `Start_Here.ipynb` in the Jupyter environment.
2. **Schema Pre-Flight Validation:** 
   - The `SubprocessBroker` silently queries the local installation paths of `CoChem-TOPOS`, `CoChem-TORQ`, `CoChem-SpycFit`, and `CoChem-SCRIBE`.
   - It hashes their internal schema versions and compares them against `cochem_deployment_manifest.json`.
   - **Decision Gate:** If schemas do not match, the cell turns red, execution halts, and a prompt demands the user to run `git pull` across all repositories. If they match, a green indicator appears.
3. **Hardware Calibration (One-Time Execution):**
   - The `HardwareProfiler` detects the physical CPU/GPU environment (`nvidia-smi` or CPU flags).
   - A rapid 5-minute wB97X-D4 benchmark is executed in the background.
   - The benchmark establishes a scalar metric (TFLOPS), tying the computational capabilities directly to the **10-Tier Temporal Matrix** (e.g., Tier 3: 1 hour on RTX 3090 $\neq$ 1 hour on 2-core CPU).
4. **QCxMS Profiling:** 
   - The `HardwareProfiler` verifies the presence and parallel compilation status of `QCxMS` binaries to unlock the Mass Spectrometry regime. If missing, the MS tiers are disabled in the UI.

## Stage 2: User Parameter & Molecule Intake
1. **Molecule Input:** The user pastes a SMILES string or uploads an `.xyz` Cartesian coordinate file into the UI widget.
2. **Execution Time-Tier Selection:** The user selects their maximum computational budget from the UI dropdown (Tier 1: 10 seconds $\rightarrow$ Tier 10: 1 Month).
3. **MLFF Element Parsing & Fallback Triage:**
   - The `intake` parser analyzes the elements present in the `.xyz` file.
   - **Decision Gate:** Does the molecule contain transition metals or elements outside the `MACE-OFF24m` training boundary?
     - *Yes:* UI logs a fallback warning, routing primary forcefield calculations to `AIMNet2`.
     - *No:* System retains `MACE-OFF24m`.
4. **Hardware Degradation Check:** 
   - Does the hardware profile lack CUDA?
   - *Yes:* If executing on a CPU (e.g., Codespaces), MACE tensor inference is bypassed. A didactic UI popup explains the hardware limit and automatically routes the system to semi-empirical `g-xTB`.

## Stage 3: Dynamic Config Generation & Keyword Scrubbing
1. **Methodology Matrix Compilation:** `cochem_core_config_compiler.py` begins assembling the `ORCA` execution blocks based on the parameters selected.
2. **Composite BSSE Scrubbing:**
   - Does the selected method (e.g., `r2SCAN-3c` or `wB97X-3c`) intrinsically utilize geometrical counterpoise (gCP)?
   - *Yes:* The compiler forcibly strips any user-provided `%geom Counterpoise` blocks to prevent mathematical overcorrection.
   - Does the method trigger the Complete Basis Set (CBS) limit or `TightPNO DLPNO-CCSD(T)`?
   - *Yes:* The compiler overrides and suppresses Counterpoise.
3. **Linear Dependence Protections:**
   - Are diffuse basis sets (e.g., `aug-cc-pVTZ`) detected in the input?
   - *Yes:* The compiler automatically injects the `AutoAux` and `DefGrid4` (if RIJCOSX is active) keywords into the `.inp` file.
4. **ExtremeSCF Guardrails:** For any single-point energies generated, the compiler appends `ExtremeSCF` to strictly enforce wave-function convergence.

## Stage 4: HDF5 Shared State Orchestration
1. **Deprecating Flat JSONs:** The orchestrator transitions out of the setup phase.
2. **Tensor Initialization:** `cochem_core_registry_manager.py` spawns `cochem_state.h5`.
3. **Data Anchoring:** 
   - The baseline `.xyz` geometries, the selected Time-Tier budget limit, the hardware capabilities, and the exact compilation strings generated in Stage 3 are saved as the initial datasets in the HDF5 archive.
   - A lock file is generated to allow memory-mapped (`mmap`) multiprocessing.

## Stage 5: Execution Handoff & Asynchronous Tethers
1. **Spawning SCRIBE Daemon:** The orchestrator silently initializes the `CoChem-SCRIBE` background archiving daemon. This daemon attaches to `cochem_state.h5` and begins pushing memory-aware Zstandard (`.tar.zst`) chunks to the SSD, ensuring total data persistence even if the Jupyter kernel segfaults.
2. **Spawning Job Manager:** `cochem_core_job_manager.py` utilizes `asyncio.subprocess` to spawn the actual quantum engine calls (ORCA/MACE).
3. **The Temporal Tether:**
   - The Job Manager sets an asynchronous timer corresponding to the user's selected Time-Tier.
   - The manager actively polls the `ORCA` convergence progress via `ZeroMQ`.
   - **Decision Gate (Termination):** If the calculation breaches the time limit before converging, the Job Manager executes a `SIGTERM`. If unresponsive after 10 seconds, it escalates to `SIGKILL`. It then triggers a graceful failover logging the timeout to the HDF5 state.
4. **Phase 1 Handoff:** With the background tethers established and the data safely memory-mapped in HDF5, `CoChem-BASE` formally hands execution flow over to `CoChem-TOPOS` to begin the combinatorial `GOAT` loop.
